# worktree-pane — 목적 & 유스케이스 재정의 (draft)

> 2026-06-07. 기능이 누적되며 복잡해진 스킬을 목적부터 다시 정의하기 위한
> 작업 문서. 확정되면 SKILL.md / README 를 이 문서에 맞춰 재정렬한다.

---

## 1. 목적 (한 문장)

**티켓/브랜치 단위의 격리된 작업 공간(git worktree)을 만들고 — 그 공간에서
"누가(어느 세션이) 작업할지"를 환경에 맞게 연결한다.**

- 격리: 메인 체크아웃(develop)은 절대 오염되지 않는다
- 연결: 호출 환경이 곧 의도 신호 — mux 안이면 새 pane+새 세션, mux 밖이면
  이 세션이 `git -C` 로 처리 (§2 축 A). 둘 다 오염 없음

## 2. 동작을 결정하는 두 축

> **핵심 교훈.** "왜 워크트리를 쓰는가"(동기)와 "도구가 어떻게 동작하는가"
> (pane 정책)를 섞어 본 것이 그동안의 혼란의 정체였다. 동기 분류(인터럽트/병렬/
> 에픽-하위/리뷰·비교·실험)는 *상황 사례*일 뿐, 도구 동작을 가르지 못한다.
> 동작은 아래 **두 축**으로만 결정된다.

### 축 A — 호출 환경 (mux 감지 = 의도 신호)

cmux/tmux 안이냐 밖이냐는 단순한 가능/불가능이 아니라 **사용자의 멘탈모델
신호**다. "mux 없음 = degradation(강등)"이 아니라 **두 개의 정상 모드**다.

| 호출 환경 | 의도 신호 | 동작 | 오염 |
|---|---|---|---|
| **mux 안** (cmux/tmux 세션 내부) | "pane 으로 벌려서 일한다" | **새 pane + 새 세션** | 없음 (별도 프로세스) |
| **mux 밖** (순수 터미널/IDE) | 단일 흐름 | **이 세션이 `git -C`+절대경로로** 처리, 맥락 유지 | 없음 (cd 안 함, 원칙 4·5) |

- 두 모드 다 **세션 오염 없음.** 차이는 "맥락을 새 세션에 넘기느냐(mux 안) vs
  이 대화 맥락 그대로 처리하느냐(mux 밖)"뿐.
- ⚠️ 감지 한계: cmux 는 PATH 에 있기만 하면 mux=cmux 로 잡혀, "설치돼 있으나
  세션 밖" 호출을 오판할 여지 (백로그 #10).

### 축 B — 동사 (의도 표현)

| 사용자 표현 | 동작 |
|---|---|
| "8494 **작업해줘** / 열어줘 / 시작해줘" | 공간 만들고 들어감 → 축 A 에 따라 새 pane or `git -C` |
| "에픽 **다음 하위 진행해줘**" | 이전 스포크 정리(삭제) + 다음 스포크 시작 (순환) |
| "그 브랜치 **확인/비교/봐줘**" | 즉답 점검 → 보통 이 세션이 `git -C`. (나란히 비교는 pane 2개가 유용) |

→ "어디서 열까?"의 답은 **축 A + 축 B 로 거의 결정**된다. 어제 추가했던 질문
단계는 두 축을 못 읽었을 때의 보상 장치였고, 이제 질문은 정말 모호할 때만
fallback 으로 둔다 (Q1·Q2 답).

### git -C 패턴 (축 A 의 mux 밖 동작)

세션을 worktree 로 `cd` 하지 않고(원칙 4) 그 브랜치를 조작하는 방법:

| 작업 | 방법 |
|---|---|
| git 명령 (status/add/commit/log/diff) | `git -C <worktree> ...` |
| 파일 수정 | Edit 에 **절대경로** |
| 빌드·테스트 (`./gradlew` 등 비-git) | `(cd <worktree> && ...)` **서브셸** — 현재 셸 CWD 불변 |

`-C` 는 git 명령에만 통하므로, 비-git 작업은 절대경로/서브셸로 보완한다.
읽기 점검은 전부 git 이라 `-C` 만으로 끝나고, 쓰기 작업을 mux 밖에서 할 땐
세 가지를 조합한다.

### 2.2 워크트리 간 관계는 도구 책임이 아니다 (범용성 경계)

에픽-하위는 워크트리들이 서로 **종속**한다는 점에서 순수 병렬과 다르다 —
"이 하위의 base 가 어느 에픽인가"를 누군가는 알아야 한다. 하지만 그 관계의
SSOT 는 **이슈 트래커(JIRA 등)** 에 있지 git 워크트리에 있지 않다.

→ **worktree-pane 은 JIRA 를 모르는 범용 도구로 남긴다.** 관계 인지·base
추론은 상위 오케스트레이션(예: `wsx:jira-progress`, MCP 로 parent epic 조회)의
책임이고, 이 스킬은 그 결정을 받아 "공간을 만들/지울" 뿐이다.

| 책임 | 주체 |
|---|---|
| 에픽-하위 관계 파악, base 결정 | 상위 스킬 / 이슈 트래커 (SSOT) — JIRA 안 쓰면 사용자가 직접 |
| 워크트리 생성·삭제·표시 | worktree-pane (L1) |

- 도구가 자체적으로 해줄 수 있는 최대치: 신규 브랜치 base 후보에 **살아있는
  워크트리 브랜치**를 올려 사용자가 에픽을 한 번에 고르게 하기 (백로그 #9).
  이건 JIRA 비종속이라 범용 도구에 넣어도 안전하다.
- 도구에 JIRA/MCP 결합을 넣지 않는다 — JIRA 안 쓰는 사용자가 못 쓰게 된다.

### 부록 — 동기 사례 (narrative, 동작 결정에는 무관)

사용자가 워크트리를 원하는 전형적 상황. 분류일 뿐 도구 분기와 무관하다.

- **인터럽트** — 핫픽스가 끼어듦. 끝나면 삭제하고 복귀 (U3·U5 빈도 높음).
- **병렬 작업** — 여러 티켓/에이전트를 동시에 살려둠. 이 스킬의 주력.
  빌드·캐시 분리, 전환 비용 제거는 여기서 공짜로 따라오는 속성.
- **에픽-하위 (허브-스포크)** — 에픽 브랜치(허브)를 살려두고 하위 브랜치를
  순회. 워크트리 간 **종속 관계**가 있다는 점에서 순수 병렬과 다르지만(§2.2),
  base 가 **에픽 브랜치**라는 것 외에 도구 동작은 동일하다.
- **리뷰 / 버전 비교 / 실험** — 받은 MR 을 빌드·검증, 두 브랜치 나란히 비교,
  깨질 스파이크. 가벼운 점검은 `git -C` 로, 병렬로 살려둘 땐 새 pane.

```
에픽-하위 구조:
메인 체크아웃 (develop)
└── 에픽 워크트리 (feature/EPIC-100)      ← 허브, 에픽 끝날 때까지 유지
    ├── 하위 워크트리 (SELLERSYS-101)     ← 끝나면 삭제
    ├── 하위 워크트리 (SELLERSYS-102)     ← 리뷰 대기 중에도 생존
    └── ...
```

## 3. 계층 — 어디까지가 코어인가

| 계층 | 책임 | 비고 |
|---|---|---|
| **L1 코어** | worktree 생성·목록·삭제 + 브랜치 해석(로컬/원격/신규) | mux 와 무관, 항상 동작. 검증 결과 견고 |
| **L2 표시** | 만든 worktree 를 어디에 보여줄까 — pane, 안내문 | 복잡도·버그의 대부분이 여기서 발생 |
| **L3 세션 규율** | 세션 오염 방지 (no-cd, 복귀, 삭제 가드) | Claude 사용 시에만 의미 |

> 진단: 오늘까지의 혼란은 L2/L3 을 L1 과 같은 비중으로 다루면서 생겼다.
> L1 은 "사실"의 영역, L2/L3 은 "정책"의 영역 — 분리해서 논의해야 한다.

## 4. 액터 & 환경 매트릭스

환경 = 의도 신호 (§2.1). "없음"은 강등이 아니라 정상 모드.

| | mux 안 (cmux/tmux 세션) | mux 밖 (순수 터미널/IDE) |
|---|---|---|
| **Claude 경유** | 새 pane + 새 세션 (주 시나리오) | 이 세션이 `git -C`+절대경로로 처리, 맥락 유지 |
| **터미널 직접** | 스크립트가 pane 까지 열어줌 | 준비 + `cd` 안내 |

## 5. 유스케이스 (재정의)

### U1. 열기 — "이 티켓 작업 시작/재개"

- 입력: 티켓명(`SELLERSYS-1234`) 또는 경로
- L1: 브랜치 해석 → worktree 준비 (신규 브랜치만 확인 질문)
  - 신규 브랜치 base 후보에 **살아있는 워크트리 브랜치(에픽)** 포함 (백로그 #9)
- L2: **어디서? — 두 축으로 결정, 질문 아님** (§2)
  - 축 A(mux 안): 새 pane + 새 세션 (기본)
  - 축 A(mux 밖): 이 세션이 `git -C`+절대경로로, 맥락 유지
  - 축 B("확인/비교/봐줘"): 즉답 점검은 `git -C`
  - 축 B("다음 하위 진행"): 이전 스포크 정리 + 다음 스포크 시작
  - 모호할 때만 fallback 질문
  - ~~이 세션이 계속 작업~~ → 축 A(mux 밖)이 정식 흡수 (구 A3, no-cd 로)
  - ~~준비만~~ → 명시 요청 전용 (구 A5)

#### U1-a. 전환 — "다른 워크트리 열어줘" (= 열기의 한 갈래, 닫기 불필요)

"다른 거 열어줘"는 별도 닫기 없이 자연스러운 전환이다. 이전 워크트리는
비파괴적으로 그대로 남는다 (U4 닫기를 암묵 흡수 — 명시 닫기 호출은 드묾).

| | 동작 | 이전 워크트리 |
|---|---|---|
| **mux 안** | 이미 열린 pane/workspace 로 **포커스 이동**, 없으면 새 pane (기존 idempotent 동작) | pane 그대로 살아있음 (재포커스 가능) |
| **mux 밖** | 이 세션의 `git -C` 타깃이 새 워크트리로 이동 | 손 떼면 끝 (디렉터리·브랜치 그대로) |

### U2. 목록 — 독립 UC 아님, U1/U3 의 보조 단계 (Q4 결정)

**"목록만 보기"는 필요한 UC 가 아니다.** 목록은 항상 무언가를 하려고(열기
U1 / 삭제 U3) 보는 것이지, 보는 것 자체가 목적인 경우는 드물다. 따라서 U2 는
독립 UC 가 아니라 U1/U3 안의 **helper** 다.

- 사용자가 대상을 특정 못 했을 때(예: "워크트리 뭐 열까", "하나 지워줘") 후보를
  **표로** 제시하고, 사용자가 이름을 말하면 U1(열기)/U3(삭제)로 합류.
- 기존 SKILL.md 의 "무조건 라디오 픽커" 강제는 **버린다**: 표를 봐도 사용자가
  "8494 열어줘"로 이어가면 되므로 dead-end 아니고, 픽커는 오히려 선택을 강제
  + 4개 제한이 걸린다 (이 세션 첫 턴 실제 마찰). 표는 개수 제한 없음.
- 굳이 "그냥 목록만"을 원하면 표 한 번 보여주면 끝 — 별도 기능·픽커 불필요.

### U3. 삭제 — "이 티켓 끝났다"

- 디렉터리 삭제 + pane 닫기, **브랜치는 보존**
- dirty 면 NEEDS_FORCE 확인 (검증 통과)
- 모호어("종료/닫아줘") → 의도 확인 후 진행
- 세션 CWD 가 대상 안이면 cd 복귀 먼저 (pwd 검증)
- 인터럽트·에픽-하위에서 빈도 높음: 완료 → 삭제 → (에픽-하위) 다음 하위 생성 루프

#### U3-a. 정리 — "끝난/묵은 워크트리 치워줘" (배치 삭제)

병렬·에픽 순회를 하다 보면 완료됐는데 안 지운 워크트리가 쌓인다. 핵심은
**도구가 "지워도 되는지"를 자동 판별하지 않는다**는 것 — 상태를 정직하게
분류해 표로 보여주고, **삭제 판단은 사람이** 한다.

워크트리는 세 상태로 나뉜다:

| 상태 | merged? | 마지막 커밋 | 판단 |
|---|---|---|---|
| **완료** | ✅ base 에 머지됨 | — | 안전한 삭제 후보 |
| **활성** | ❌ | 최근 | 살아있어야 함 — 후보 아님 |
| **회색지대** | ❌ | 오래 전 | **홀딩(보류)인지 방치된 쓰레기인지 도구는 구별 못 함** → 사람만 안다 |

- **머지 감지 = 두 신호의 OR** (설정 없이 모든 팀 커버 — 범용 도구이므로):
  | 머지 방식 | `git branch --merged <base>` | upstream gone |
  |---|---|---|
  | merge commit (우리 팀) | ✅ 주 신호 | ✅(보통) |
  | squash / rebase (다른 팀) | ❌ | ✅ 주 신호 |
  - squash 팀은 브랜치 커밋이 다른 SHA 로 들어가 `--merged` 가 못 잡지만,
    MR 머지 후 원격 브랜치가 삭제돼 **upstream gone**(`fetch --prune` 후
    `: gone`)으로 잡힌다. 둘 중 하나만 걸려도 "완료".
  - **선행 필수: 정리 전 `git fetch --prune`** — base 최신화 + 원격 삭제 반영.
    안 하면 방금 머지된 것도 미머지/살아있음으로 보임.
  - 둘 다 안 걸리면 회색지대 → 사람 판단. (upstream-gone 감지는 upstream 이
    자기 원격 브랜치를 가리켜야 정확 → 백로그 #1 선결.)
- **표시 = 상태 라벨 + 보조 정보.** `merged` / `활성` / `미머지·N일 경과` 를
  구분 표시. 시간(`%cr`)은 보조일 뿐 삭제 기준 아님.
  - 회색지대를 시간만으로 자동 삭제하면 **홀딩을 실수로 날린다** — 절대 금지.
- **실행 = 표 → 선택 → 삭제** (helper U2 → U3): 사용자가 라벨 보고 골라 삭제.
  자동 일괄 삭제 안 함.
  - **AskUserQuestion 4개 제한 비해당** — 픽커가 아니라 **표**라 개수 무제한.
    사용자가 "1·3·5 지워줘" / "merged 인 거 다" 처럼 자유롭게 지정 (Q4).
  - **삭제 직전 재확인 필수**: 고를 때 한 번, **실제 삭제 직전 대상 목록을
    다시 보여주고 한 번 더 확인**(2-step). 배치라 한 번에 여럿 지우므로
    오삭제 방지. dirty 보호(NEEDS_FORCE)·브랜치 보존 등 U3 규칙 그대로.
  - 고아 등록은 `git worktree prune` 도 함께 (백로그 #8).
- 신규 기능 — 백로그 #11.

### U4. 닫기 — "화면/주의만 정리" (≠ 삭제)

"닫기"는 **비파괴적 주의 전환** — worktree 디렉터리·브랜치는 그대로 살아있고,
보던 것에서 손을 떼는 것뿐이다. "열기"처럼 환경에 따라 의미가 갈린다.

> **명시 호출 빈도는 낮다.** 닫고 싶을 때는 보통 "다른 워크트리 열어줘"로
> 표현되고, 그건 닫기가 아니라 **전환**(U1-a)이라 이전 것이 비파괴적으로
> 남는다. 순수하게 "아무것도 안 열고 화면만 비우기"는 드물고, 그땐 mux
> 단축키면 충분 — Q3 비스코프 결정을 뒷받침한다.

| | 열기 (open) | 닫기 (close) |
|---|---|---|
| **mux 안** | 새 pane + 새 세션 | **pane 닫기** (mux 책임 — 비스코프, Q3) |
| **mux 밖** | 이 세션이 `git -C <worktree>` 로 작업 | **이 세션이 base(메인 체크아웃)로 타깃 복귀** |

- **mux 안 → pane 닫기는 도구 비스코프 (Q3).** worktree 생명주기 ≠ pane
  생명주기. pane 닫기는 mux 가 더 잘함(cmux `close-surface`, tmux `Ctrl-b x`)
  이고, 여는 것과 달리 닫기엔 도구가 묶어줄 게 없다. worktree 가 여러 pane 에
  흩어지는 일도 거의 없어 "전부 닫기" 명분도 약함 → mux 단축키 안내로 처리.
- **mux 밖 → base 로 주의 복귀.** 원칙 4 때문에 세션은 애초에 워크트리로 `cd`
  한 적이 없다(CWD 줄곧 메인). 그러니 "닫기" = `git -C <worktree>` 를 그만
  쓰고 평소 git(= 메인 체크아웃 = base)으로 돌아가는 것. **파일시스템상 아무것도
  안 바뀐다** — `-C` 를 안 붙이면 끝.
- **닫기 ≠ 삭제(U3).** 어느 환경이든 닫기는 비파괴적이 기본. 삭제는 명시어
  (삭제/remove/delete)일 때만 — 그래서 "닫아줘"는 의도 확인이 맞다(원칙 2).
- ⚠️ `--close`/`--rm` 가 `--remove`(삭제) 별칭인 함정(백로그 #3)은 반드시
  제거 — "닫아줘"가 삭제로 오인되는 CLI 레벨 위험.

### U5. 복귀 — "메인/이전 세션으로"

- 브랜치 복귀가 아니라 **디렉터리 복귀**: 메인은 develop 을 떠난 적 없음
- 세션 복귀: 메인 경로에서 `claude --continue` / `--resume`, `/clear` 후엔 `/resume`
- worktree 는 삭제 없이 그대로 둬도 무비용
- M2b: 복귀 대상이 메인이 아니라 **에픽 워크트리(허브)** 일 수 있음

## 6. 원칙 (불변 규칙)

1. 새 브랜치는 무단 생성 금지 — 반드시 확인
2. **닫기 ≠ 삭제.** 닫기는 비파괴적 주의 전환(pane 닫기 / base 복귀, U4),
   삭제는 디렉터리 제거(U3). 삭제는 명시어(삭제/remove/delete)만 — 모호어
   ("닫아줘/종료")는 의도 확인
3. 브랜치는 삭제하지 않는다 (명시 요청 제외)
4. **세션은 worktree 로 cd 하지 않는다** — 절대경로 + `git -C`
5. `git -C` 전에 대상 검증 (`rev-parse --show-toplevel`) — 고아 디렉터리 fallback 함정
6. **범용성 유지** — JIRA/MCP 등 특정 트래커에 결합하지 않는다. 워크트리 간
   관계 인지는 상위 레이어 책임 (§2.2)
7. **선택지가 많으면 픽커 대신 표 + 자유 응답.** AskUserQuestion(라디오)은
   4개 제한이 있으므로, 후보가 그보다 많을 수 있는 곳(워크트리 목록, base
   후보 등)은 라디오로 강제하지 말고 **표로 전부 보여주고** 사용자가 이름/번호로
   자유롭게 답하게 한다. 라디오는 후보가 적고 선택 의도가 명확할 때만.
8. **디렉터리 이름 ≠ 브랜치 이름.** 워크트리 디렉터리는 브랜치의 **basename**
   으로 짓는다(디렉터리에 `/` 불가). 그래서 prefix(`feature/`·`hotfix/`)는
   **디렉터리엔 안 보이고 브랜치엔 그대로 살아있다.** 예: 브랜치
   `hotfix/SELLERSYS-9999` → 디렉터리 `.claude/worktrees/SELLERSYS-9999`.
   - 결과: 디렉터리만 보면 prefix 구분 불가 → `feature/X` vs `hotfix/X` 는
     같은 basename 으로 충돌(가드가 실제 브랜치 확인해 거부, #4). 동시 보유는
     `--root` 로 분리.
   - `--list` 는 `path<TAB>branch` 로 **브랜치까지** 출력하므로 목록에선 구분됨.
